# 大数据包恢复方案

状态：待批准设计，未实现。关联 AUDIT.A03；当前修复仅覆盖既有同步字节预算内的完整往返。

## 问题与既有能力

`JournalEntry` 的描述、短评和 JSON 值可以形成超过 `IMPORT_FILE_MAX_BYTES` 的合法导出。提高条数或把 2 MiB 改成更大的常数，仍会留下同一种缺口；单个条目本身也可能超过一次请求预算。

当前 `ImportEntriesView` 读取整个请求，`DataBundleSerializer` 完整预检，`import_data_bundle` 在 owner 锁和一个数据库事务内恢复至空手账。它没有分块上传、持久预检或恢复进度能力。`ExternalImportSession` 依赖外部 provider、认证连接及收藏 snapshot，apply 支持逐项失败并把完整 snapshot 放在 JSON 字段；复用其接口会改变外部收藏导入合同，也不能解决大字段的内存占用。

现有 [长任务隔离记录](../concurrency-long-task-isolation-v1.0.md) 将 Background Job 边界列为后续工作。该历史观测不作为本方案的性能通过证据；本方案也不新增通用 Worker、消息队列或发行操作。

## 推荐兼容路径

1. 保留 Data Bundle v1 的完整 JSON 字节及所有字段；新增独立、认证的恢复会话传输 API。客户端按字节上传分块，单个条目可以跨块；服务端完成摘要和顺序校验后再解释 JSON。用户仍选择一个完整导出文件。
2. 会话绑定创建用户、预期大小、内容摘要、接收偏移、状态和过期时间。分块落入受控私有暂存区，设置每用户/实例的磁盘配额和并发预算；不将完整 JSON 或认证连接凭据塞入会话记录。重复块必须字节等价，错序、摘要冲突、过期或其他 owner 的请求不得推进状态。
3. 完整接收后使用有界解析与暂存预检，复用当前字段、身份唯一性和 Core history 冲突规则。预检输出绑定原始摘要和版本，包含所有记录的总数和错误；未通过前不创建可见手账条目。预览分页只改变展示，不能只校验当前页。
4. 提交时重新获取 owner 锁，确认目标仍为空及预检摘要/状态有效。单次事务恢复全部条目和关系，并与会话完成结果一同提交；重试返回同一结果。失败清理未提交结果并保持目标为空。若实测无法在批准的锁时长和事务预算内完成，需另行批准“暂存手账版本 + 一次发布”的数据库/read-path 合同，不能改成对真实手账逐批提交。
5. 暂存数据在成功、明确取消、过期或失败清理后删除。恢复结果不包含原始数据或内部路径；日志只记录必要的状态、数量和安全错误码。一次成功不会使原始用户数据失效，上传媒体二进制仍不属于此 portable JSON 格式。

## 需要批准的具体合同

- 新恢复会话 API、状态机与数据库 migration，以及与既有外部导入会话独立的职责。建议状态顺序为 receiving → validating → ready → applying → completed，并为 failed/cancelled/expired 定义终态。
- 暂存路径的 authority、所有权、寿命、磁盘配额、并发和清理机制，以及丢失暂存文件时的可重试行为。
- 大字段与总数据量的资源预算如何覆盖普通写入接受的合法数据；若新增领域上限，须先给出既有合法值的兼容策略，不能在恢复时静默拒绝或缩短。
- 提交的锁时长/事务预算、客户端断线后的状态查询与幂等重试；若需要后台执行，接入经批准的 Background Job 边界及取消语义。

## 必须验证的行为

使用真实 PostgreSQL、可控断点和独立 HTTP 客户端，覆盖超过 2 MiB 的单条字段及多条集合、Unicode 跨块、乱序/重复/缺块、摘要错误、完整预检失败、owner 越权、预览后手账被写入、并发提交、提交中断与重试、事务回滚、过期清理、磁盘满和正常 API 负载。恢复前后比较完整稳定领域值、关系、计数与顺序；分别记录峰值内存、暂存字节、锁时长、总时间和失败后的可见数据。

这些合同获批并通过验证前，超过同步预算的合法数据包仍是明确未解决项，不能登记为 AUDIT.A03 全面关闭。
