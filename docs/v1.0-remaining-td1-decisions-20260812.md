# AniMemo v1.0 Remaining TD1 Decision Dossiers — 2026-08-12

## Decision scope

本记录只收敛 `DA-TD1-001` 与 `DA-TD1-004`。本轮没有修改 runtime、SDK、Integration Protocol、数据库 schema、CI 或生产环境；决定依据是当前已冻结的 v1.0 contract、真实 implementation、既有 tests 与已合并 closure seams。

两项都不是 `BLOCKED`：它们被正式记录为 `ACCEPTED V1.0 DEBT EXCEPTION`。这表示 v1.0 保留已知、受补偿控制的实现债务，并把触发条件、兼容约束和未来 remediation 写入 v1.1 计划；它们仍然是 TD1，不被降级为 TD2。

## DA-TD1-001 — Plugin SDK / Runtime v3 可序列化边界

### Decision

**ACCEPTED V1.0 DEBT EXCEPTION**。

v1.0 冻结的是 SDK API `2`、Manifest `schemaVersion: 2` / `sdkApi: 2`、actor-bound Core capability、JSON-value DTO、storage/settings extension、error codes、package immutability 与 trusted in-process Python runtime。v1.0 没有承诺 backend plugin handler、filesystem root、Django transaction、QuerySet、Python callback 或任意网络调用可直接跨进程序列化。

因此不在 v1.0 通过 flag-day 重写官方插件、路由 handler 和 Host storage；当前问题作为 Runtime v3 implementation debt 接受，而不是把未来 RPC 边界误报成现有 SDK contract failure。

### Original finding

`PluginContext.root` 是宿主路径对象，`request_json()` 使用 `requests`，`PluginDispatch` 把 DRF `request` 交给 plugin handler，`PluginStorage.collection()` 返回 Django QuerySet；官方 `watch-history-importer` 仍使用 Django settings/transaction/timezone、DRF `Response/status` 与直接 `requests`。这些对象和 ambient lifecycle 不能直接成为 worker/container/RPC message。

### Current evidence

| Surface | Current implementation | Contract classification |
| --- | --- | --- |
| Core capabilities | Journal、Watch History、Analytics 以 actor-bound capability 暴露，返回 DTO/统计值，不返回 ORM 对象 | v1.0 frozen interface，PASS |
| Manifest/enforcement | 未声明 capability、settings 或 storage 时由 Host 拒绝；USER installation 与 actor 每次调用校验 | v1.0 security/tenant boundary，PASS |
| Backend route | Host-owned router 解析 path，trusted in-process handler 接收 DRF request，可返回 DRF Response/tuple/payload | trusted runtime implementation；不是 v1.0 RPC contract |
| Storage/settings | Host 提供 namespaced storage 与 settings facade；内部仍由 Django implementation 支撑，storage collection 是 QuerySet | internal leakage，Runtime v3 debt |
| Official plugin | Core mutation/read 通过 Host capabilities；Web presentation、batch transaction、Bangumi network helper 仍依赖当前 Django/DRF/requests runtime | reference consumer remains v1.0 trusted runtime |
| Package/runtime | superuser review/publish、`slug + version` immutability、runtime reconciliation、package gates | compensation boundary，PASS |

### Current consumers

- Dynamic backend plugin routes through `PluginDispatch` and the Host-owned `PluginApi` router.
- Official `watch-history-importer 0.4.2` Web handlers, Integration actions, Host storage/settings, Journal and Watch History capabilities.
- Runtime hook registration and lifecycle reconciliation through `RuntimeRegistry`.
- Plugin package validation, immutability, install/enable/disable, capability and runtime end-to-end tests.

### Breaking change risk

Complete portability closure would change the handler input/result surface, storage collection operations, network access, transaction/batch behavior and official plugin imports. That is a versioned SDK/runtime migration risk, not a safe v1.0 implementation-only correction.

### Why this is TD1

它影响未来 worker/container/RPC 的 seam depth：如果不先定义 serializable message，Runtime v3 会同时重写 Host、official plugin、storage、request transport、network broker、transaction/batch semantics 和测试。影响面是高的，但风险发生在未来隔离运行时的迁移，不是当前 trusted in-process v1.0 调用的已证实 correctness、auth 或 data-integrity failure。

### Root-cause classification

- **A — frozen interface error：否。** SDK v2 明确冻结了 capability/DTO/actor/error/package 语义，但没有把当前 in-process route handler 宣称为 RPC interface。
- **B — bypass of frozen boundary：有限且不构成 v1.0 contract breach。** 官方插件仍通过 Host capability 访问 Core 数据和 mutation；直接 Django/DRF/requests 是受信任 runtime implementation 的 ambient authority，`dataPolicy` 也明确不是 OS sandbox。
- **C — legacy/internal leakage：是。** Django transaction/settings/timezone、QuerySet、DRF request/Response、filesystem root 与 callback identity 泄漏到未来 portability seam。
- **D — versioned migration debt：是。** 真正收口需要新的 DTO/Host API 与官方包迁移，必须通过新的 SDK/package version，不得改写已发布 `watch-history-importer 0.4.2`。

### Alternatives

1. **v1.0 立即实现 B1/B2/B3：** 新增 JSON request/response/error DTO、Host storage operations、transaction/batch capability、network broker，并迁移官方插件。技术方向正确，但会改变现有 handler contract、官方插件包和测试/发布边界，属于 SDK/runtime breaking migration。
2. **新增并行 SDK v3 adapter：** 保留 SDK v2 trusted runtime，同时提供可序列化 v3 surface，官方插件在新版本迁移。风险最低，但属于 Runtime v3/v1.1 设计与实现，不应伪装成 v1.0 closure。
3. **接受 v1.0 例外并保持 v2 trusted in-process：** 选择项。冻结当前可验证的 capability/tenant/package boundary，把 portability debt 绑定到明确触发条件。

### Why option 3

它保留已发布插件 `0.4.2`、SDK API `2`、Manifest v2 和现有 integration/web behavior；同时不制造一个只做名称转换、却无法解决 transaction/network/storage semantics 的浅 adapter。当前 architecture tests、plugin package gates、runtime lifecycle tests 与 capability tests 保护的是 v1.0 真正承诺的边界，足以支持例外而不声称 Runtime v3 已完成。

### Lowest-risk option

保持 SDK v2 与 trusted in-process implementation，明确把完整可序列化 seam 留到带版本的新 Runtime v3/SDK v3 phase；不新增没有现实 consumer 的永久双轨 adapter。

### Can resolve without breaking contract

**不能完成完整 closure。** 可以继续改善内部 locality，但不能在不改变现有 handler、storage、network 和 transaction assumptions 的前提下让当前官方插件成为可迁移 RPC consumer。完整解决需要 versioned SDK/runtime boundary。

### Recommended v1.0 action

接受例外，保持现有 v1.0 public semantics 与 trust model；保留 contract/package/capability/runtime gates，并在首次 worker/container/RPC 或不受信任 backend publisher 之前启动 v1.1 remediation。

### Exception eligibility

- No TD0 consequence: **yes**。
- No current correctness bug: **yes, based on current trusted in-process contract and tests**。
- No current security weakness: **yes, within the explicitly trusted-superuser runtime model**。
- No data-integrity risk: **yes, Core data access remains actor-bound and service-owned**。
- No production instability introduced by this decision: **yes; no runtime behavior changes**。
- No forced breaking change immediately after v1.0: **yes; the trigger is future Runtime v3/isolation expansion, not routine v1.0 operation**。

### Compatibility

不会改变：

- SDK API `2`、Manifest `schemaVersion: 2` / `sdkApi: 2`；
- Core capability 名称、actor binding、enabled installation、DTO/error semantics；
- `host.api` trusted in-process route handler contract；
- `host.storage`、settings、Integration action/event semantics；
- official plugin `slug + version` identity，尤其是 `watch-history-importer 0.4.2`；
- API v1、Auth、Resource Identity、Integration Protocol v1。

### Risk

接受例外会保留未来隔离迁移成本，并允许受信任 backend plugin 继续依赖 Django/Python ambient authority。该风险由 publisher trust model 和 Host capability enforcement 限定；它不是 v1.0 的 sandbox promise。若未来开放不受信任 publisher、第三方 backend marketplace 或多进程 runtime，例外必须在触发点前关闭。

### Compensation controls

- backend runtime 继续是 superuser review/publish 后的 trusted in-process Python code；
- package `slug + version` immutable，内容变更必须使用新 SemVer；
- Manifest 声明、安装/启用状态、actor binding 和 capability enforcement 每次调用都生效；
- Core journal/watch-history/analytics 不提供 generic database capability，Core mutation 继续由 authoritative service 拥有；
- `dataPolicy` 继续作为审计声明，而不是伪装成 sandbox；
- 保持 official package validate/build/package/immutability/runtime/integration gates；
- 文档明确 `Runtime v3 worker/container/RPC` 未完成，不把当前 runtime 标成 portable。

### Future Action / Trigger / Target phase

**Trigger：** 首次启用 worker、container、RPC、跨进程 plugin execution、不受信任/第三方 backend publisher，或需要独立 runtime resource/network/secret limits 时。

**Target phase：** v1.1 Plugin Runtime v3 preparation；在该 trigger 前不得扩大 trusted runtime 的发布模型。

**Expected remediation：** 设计并 version 一个 JSON-compatible SDK v3：`PluginRequestDTO`、result/error envelope、Host-owned clock/logging/settings/storage operations、显式 transaction/batch seam、network broker、serializable hook/action/event descriptors 与 resource policy；先迁移 official plugin 为 reference consumer，再执行 package/runtime compatibility gate。SDK v2 和已发布 v2 package 不被原地改写。

## DA-TD1-004 — Integration receipt PENDING lease / replay 生命周期

### Decision

**ACCEPTED V1.0 DEBT EXCEPTION**。

v1.0 保留当前 at-most-once safety-first receipt semantics：同一 `connection + request_id` 只有一个 receipt；claim 成功后先持久化 `PENDING`，再执行 handler；并发重复请求不再次执行 handler；COMPLETED/FAILED 直接重放已存 response；PENDING 在固定等待后返回 `request_in_progress`，不自动接管、不由常规 cleanup 删除。

这留下 crash-after-claim 后的 liveness/availability gap，但没有发现当前实现会因重复等待而自动重复副作用，也没有 action-level replay contract 足以安全授权 takeover。为避免把未知副作用结果重放成第二次副作用，v1.0 不实现通用 lease takeover。

### Original finding

`IntegrationActionReceipt` 没有 owner/token/lease deadline/attempt metadata。创建 PENDING 与 handler 执行分开；进程在 claim 后退出会留下 `completed_at=NULL`。后续 retry 最多等待约 5 秒，然后永久返回 `request_in_progress`；cleanup 只处理 COMPLETED/FAILED。

### Exact state machine and claim boundary

```text
ABSENT
  └─ atomic create(connection, request_id, action)
       └─ PENDING (unique ownership exists; handler starts after commit)
            ├─ handler success → COMPLETED + response persisted
            └─ handler/normalization failure → FAILED + stable error persisted

Duplicate request while PENDING
  └─ refresh for bounded wait
       ├─ terminal state observed → stored response, replay=true
       └─ still PENDING after wait → request_in_progress 409, no handler

Terminal receipt within retention
  └─ same action → stored response, replay=true

Different action with same request_id
  └─ request_id_conflict 409

Maintenance cleanup
  └─ deletes old COMPLETED/FAILED only; PENDING remains
```

### Current replay contract

- **Receipt identity:** `(connection, request_id)`; the connection is selected by authenticated HMAC credentials, not by request payload.
- **Request identity:** `request_id` is the caller's idempotency key within that connection; `action` must match the stored action.
- **Status transitions:** `ABSENT → PENDING → COMPLETED|FAILED`; there is no `REPLAYED` database status.
- **Stored response:** terminal `response_payload`, `response_status`, `status` and `completed_at` are persisted before a later replay.
- **Replay response:** a terminal same-action receipt returns the stored payload/status with replay marker; it does not call the handler again.
- **Expiry:** completed/failed receipts are retained for the configured default seven-day period; replay is guaranteed only while retained.
- **ACK semantics:** event ACK/cursor state belongs to `IntegrationEvent`; action receipts have no ACK transition and this decision does not add one.
- **Cleanup:** routine cleanup deletes expired COMPLETED/FAILED receipts only; it deliberately leaves PENDING rows.
- **Failure behavior:** handler exceptions and invalid/oversized responses become stable FAILED receipts; they are not cached as success.

### Contract invariants

- `(connection, request_id)` is unique and connection-scoped.
- The action is part of the receipt identity check; a different action cannot reuse the key.
- A fresh claim is committed before the handler runs.
- A duplicate PENDING request never invokes the handler in the current implementation.
- Only terminal receipts provide cross-request replay; terminal response payload/status are persisted before replay.
- Oversized/invalid handler responses are converted into stable FAILED receipts rather than storing raw non-JSON data.
- Normal cleanup removes old COMPLETED/FAILED receipts and never deletes PENDING receipts.
- HMAC nonce replay protection is a separate transport invariant and is not replaced by action receipts.

### Correctness, security and data-integrity assessment

The PostgreSQL concurrency proof demonstrates duplicate concurrent delivery executes the handler once. The current weakness is liveness: a process crash after claim can make one request ID permanently unavailable until the row is handled outside the protocol. Because there is no takeover path, there is also no stale-owner finalize race in v1.0. The code does not prove that an external side effect did or did not occur before a crash; therefore automatic replay with a new owner would be unsafe for opaque actions.

This is a bounded availability debt, not a proven auth bypass, duplicate-execution bug under the current live-process contract, or receipt data-integrity corruption. It remains TD1 because recovery semantics become mandatory before high-availability workers, long-running actions or Runtime v3 increase the crash window.

### Current consumers

- HMAC-authenticated Integration Gateway callers and the `ActionsView` response/replay marker.
- Official importer Integration actions (`history-get`, `history-add`, `entries-search`, `import-preview`, `import-commit`).
- PostgreSQL concurrent duplicate callers and the Bridge's request/retry behavior.
- Maintenance cleanup and any operator inspecting receipt status/history.

### Breaking change risk

Generic takeover changes the observable meaning of a still-PENDING request: a retry could execute an opaque external side effect a second time after the original worker had already completed it. The additive database shape alone does not make that replay behavior compatible.

### Alternatives

1. **Unconditional lease takeover:** additive fields plus timeout, then any worker may reclaim PENDING. Rejected for v1.0 because a timed-out handler may have completed an external side effect and then lost its response path.
2. **Action-specific replay contract plus lease:** declare each action as `at_most_once`, `replay_safe` or an equivalent explicit policy; use claim token, lease deadline, attempt count and conditional finalize. Correct future direction, but it changes action lifecycle semantics and requires migration/tests/runbook.
3. **Keep v1.0 safety-first semantics and accept liveness debt:** chosen. Preserve no-duplicate behavior and document orphan PENDING as unknown execution outcome.

### Why option 3

The current Integration Protocol v1 already promises no duplicate side effect while the receipt is pending and explicitly excludes PENDING from routine deletion. A generic takeover would be a breaking behavioral change even if the database fields were additive. Without classifying action replay safety, the safest compatible behavior is to refuse automatic recovery rather than guess.

### Lowest-risk option

Keep the current single-claim, bounded-wait, terminal-only replay state machine and record orphan PENDING as an explicit v1.0 availability exception until action replay policy is defined.

### Can resolve without breaking contract

**不能安全完成通用 takeover。** 当前 terminal replay and duplicate suppression already preserve the frozen contract; adding a lease without action-specific replay semantics would change副作用语义。未来可用 additive fields only after the replay policy and stale-finalize rules are frozen.

### Recommended v1.0 action

接受例外，不修改 receipt schema 或 replay wire behavior；保留 PostgreSQL concurrency, receipt persistence, failure caching, response-limit and cleanup tests as compensation controls。

### Exception eligibility

- No TD0 consequence: **yes**。
- No current correctness bug in the live-process at-most-once path: **yes**。
- No current security weakness: **yes; HMAC, identity binding and action/installation checks remain enforced**。
- No data-integrity risk introduced by this decision: **yes; no receipt rewrite, deletion or replay change**。
- No production instability introduced by this decision: **yes; no runtime behavior change**。
- No forced breaking change immediately after v1.0: **yes; recovery is triggered only by multi-worker/long-running/RPC expansion**。

### Compatibility

不会改变：

- `connection + request_id` uniqueness and action conflict behavior；
- PENDING duplicate wait and `request_in_progress` 409 behavior；
- COMPLETED/FAILED response replay and `X-AniMemo-Idempotent-Replay` semantics；
- completed/failed retention and PENDING non-deletion；
- HMAC, identity binding, user installation and action declaration checks；
- Bridge cursor/ACK contract and Integration Protocol v1 wire shape。

### Risk

An orphan PENDING can block retries for that request ID indefinitely and the external caller cannot infer whether the original side effect happened. Clients/operators must treat this as an unknown execution outcome; using a fresh request ID is not a generic safe recovery for side-effecting actions. The accepted exception therefore trades liveness for at-most-once safety until action replay semantics are explicit.

### Compensation controls

- atomic unique claim prevents concurrent duplicate handler execution;
- bounded duplicate wait prevents request threads from waiting forever in one request;
- PENDING is never silently deleted or rewritten by routine maintenance;
- terminal response persistence makes normal retries deterministic;
- failed/oversized responses are cached as stable failures;
- PostgreSQL concurrency test remains an authoritative gate where supported;
- future operator recovery must inspect action-specific execution outcome before any manual retry, and must not assume a new `request_id` is safe.

### Future Action / Trigger / Target phase

**Trigger：** multi-worker crash recovery、long-running/async integration actions、automatic client retry after process failure、或 Runtime v3 worker/container rollout。

**Target phase：** v1.1 Integration reliability / Runtime v3 preparation；在 trigger 前保持当前 v1.0 safety-first behavior。

**Expected remediation：** additive receipt fields (`claimed_at`/`lease_until`/`claim_token`/`attempt_count` or equivalent), conditional claim and finalize, explicit per-action replay policy, crash-after-claim and stale-finalize tests, PostgreSQL concurrency/stateful-upgrade gates, diagnostics and operator recovery runbook. Existing receipt rows must remain readable; no destructive rewrite or blanket PENDING deletion。
