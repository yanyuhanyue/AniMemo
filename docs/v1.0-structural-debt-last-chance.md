## Accepted TD1 exceptions

### DA-TD1-001: serializable Plugin SDK / Runtime v3 boundary

SDK API 2, Manifest v2, actor-bound Core capabilities, DTO/error/package semantics, and trusted in-process execution remain frozen and tested. Current backend plugins can still depend on Django/DRF/QuerySet/transactions and arbitrary network access, so they are not portable to a worker/container/RPC boundary.

The exception remains acceptable only while backend publishers are trusted and superuser-reviewed. Before untrusted publication or Runtime v3 isolation, introduce a versioned serializable SDK, Host storage/transaction operations, and an outbound-network broker; migrate the official plugin as the reference consumer.

### DA-TD1-004: Integration receipt can remain PENDING

The state machine is safety-first and at-most-once: duplicate PENDING requests do not execute the handler again, while terminal receipts replay stored results. A crash after claim can leave a request ID permanently PENDING because there is no lease, takeover token, or action-specific replay policy.

The exception remains acceptable for the current synchronous v1.0 contract. Multi-worker crash recovery, async/long-running Integration actions, or Runtime v3 must first add action replay classification, conditional claim/finalize, and stale-owner tests.

## New TD1: trusted release authority

DeepSec broad and exact-delta analysis identified overlapping High findings where release classification, gate authority, and official package identity logic are obtained from the candidate being certified. Candidate-side consistency checks cannot alone provide an independent trust anchor.

The repository's protected-main Pre-Merge workflow is the intended compensation. It failed for exact candidate `0856572`: trusted `main` called a reusable Release Gate that lacked the candidate-required `dr-rehearsal` job, and the candidate compatibility branch did not activate for the observed event. The same release cycle also failed to complete the historical Release Producer upgrade, so immutable dry-run artifacts and RC-to-Stable parity were never produced.

Classification: **new unresolved TD1 and RC1**. The boundary affects release integrity now, not only a future Runtime v3 design.

Closure requires protected trusted code to independently recompute candidate classification/package identity, a passing exact-candidate Trusted Pre-Merge authority run, and a completed producer dry-run/parity proof.

## DR decision update

The previous report treated the complete DR state contract as missing. Candidate `0856572` now has a self-describing backup set and isolated restore rehearsal covering PostgreSQL application data, media references/files, provider and external account state, Plugin/Integration state, installation identity, setup lock, and authentication epoch rotation.

The final Release Gate includes direct backup, recovery-path, and DR contract tests plus the full disposable A-to-B rehearsal. The restored old access token is checked to be unexpired before rejection, avoiding a false PASS caused by natural token expiry. The DR gap is therefore removed from TD2 and is not a release blocker in this checkpoint.

## Deferred TD2 additions

### Immutable CI dependency pinning

Multiple GitHub Actions and service images use mutable major/version tags. This is real supply-chain debt, but the final pass did not rerun DeepSec Supply Chain and must not claim a clean dependency result. Pin reviewed actions/images to immutable SHAs/digests in a dedicated change with workflow validation.

### Backup inventory and retention

Updater backups are verified for location, regular-file identity, checksum, gzip integrity, and freshness, but automatic retention/pruning is intentionally absent. Define operator-visible inventory, capacity alerts, and a conservative retention procedure. Do not add silent automatic deletion during v1.0 closure.
