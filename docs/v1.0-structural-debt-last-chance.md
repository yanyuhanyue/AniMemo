## Accepted TD1 exceptions

### DA-TD1-001: serializable Plugin SDK / Runtime v3 boundary

SDK API 2, Manifest v2, actor-bound Core capabilities, DTO/error/package semantics, and trusted in-process execution remain frozen and tested. Current backend plugins can still depend on Django/DRF/QuerySet/transactions and arbitrary network access, so they are not portable to a worker/container/RPC boundary.

The exception remains acceptable only while backend publishers are trusted and superuser-reviewed. Before any untrusted publisher or Runtime v3 isolation, introduce a versioned serializable SDK, Host storage/transaction operations, and an outbound-network broker; migrate the official plugin as the reference consumer.

### DA-TD1-004: Integration receipt can remain PENDING

The current state machine is safety-first and at-most-once: duplicate PENDING requests do not execute the handler again, while terminal receipts replay stored results. A crash after claim can leave a request ID permanently PENDING because there is no lease, takeover token, or action-specific replay policy.

The exception remains acceptable for the current synchronous v1.0 contract. Multi-worker crash recovery, async/long-running Integration actions, or Runtime v3 must first add action replay classification, conditional claim/finalize, and stale-owner tests.

## New TD2: complete DR state contract

The repository has a verified PostgreSQL backup producer and extensive stateful-upgrade coverage, but no complete production-equivalent backup/restore set and rehearsal for all required state:

- PostgreSQL application data.
- Media objects or an independently recoverable media inventory/reference contract.
- installation/authentication recovery procedure, including post-restore authentication epoch rotation.
- Plugin CAS/package data and runtime-required state where not reconstructible from immutable release inputs.
- Updater CURRENT/PREVIOUS/history/operation evidence where operator recovery depends on it.
- Provider, external account/media, Integration, plugin installation/data, and SiteConfig verification after restore.

The Update Agent intentionally does not perform automatic database restore. That is a sound safety boundary, but it means an external operator-run restore contract and rehearsal are required. The current `pg_dump` gzip alone cannot be claimed as complete disaster recovery.

Classification: **TD2 architecture debt**, but **Final RC readiness blocker** because the user's release acceptance explicitly requires an isolated A-to-B restore proof and locked `/setup` after restore.

## Constraints carried forward

- Do not implement a generic queue solely from the existing performance baseline.
- Do not add automatic database reverse migration or automatic destructive restore.
- Do not widen trusted backend plugin publication before Runtime v3 controls exist.
- Do not delete orphan PENDING receipts generically or replay opaque side effects without an action-specific contract.
- Keep API v1, Plugin SDK v2, Integration Protocol v1, resource identity, and release manifest identity frozen.
